## 1. 逐条核查

### #1 “剔除原因参数未插值（长期 bug）”—— 症状对，归因错

`judge()` 里的 f-string 是对的，且自首个 commit 起就是对的：

```python
# screen_kline.py:1304-1307
if det["age"] > N:
    return False, f"⑦ 距启动{det['age']}日 > N={N}"
if det["vcross"] < k_vol:
    return False, f"② 启动日放量不足({det['vcross']:.2f}<{k_vol})"
```

`git log -L 1295,1310:screen_kline.py` 显示这三行只在 `0986ff5` 加过参数、在 `f7fd471`
动过上下文，从未出现过裸 `#`。

`#` 来自主流程的**统计归一化**：

```python
# screen_kline.py:1489-1496
ok, why = judge(...)
if ok:
    hit.append(det)
else:
    k = re.sub(r"[\d.]+", "#", why)      # 归一化，便于统计
    rej[k] = rej.get(k, 0) + 1
```

实测复现：

```
'⑦ 距启动4日 > N=4'          -> '⑦ 距启动#日 > N=#'
'② 启动日放量不足(1.20<1.75)' -> '② 启动日放量不足(#<#)'
'③ 启动日(2026-10-27)未通过日频条件' -> '③ 启动日(#-#-#)未通过日频条件'
```

**这比“漏填参数”更严重的地方在于**：

1. 文档承诺的是逐条明细。`K线选股规则_v3.md:405` 与 `README.md:176` 都写
   “逐条剔除明细”，但 JSON 里只有一个按 `#` 归一后的计数器，名不副实。
2. **跨版本对比会静默混淆语义**。`N`、`K_VOL`、`0.2%`、`MA60×0.98` 全部被抹成 `#`，
   所以“N=4 的 148 只”和将来“N=2 的 148 只”在结果里长得一模一样，做参数复盘时
   无法从历史 JSON 反推当时用的是哪组阈值。
3. 丢掉了唯一可用于调参的分布信息：`⑦` 的实际 `age` 分布（4/5/6…）、`③` 的实际
   日期（可反查停牌）、`②` 的实际量能比（1.20 还是 1.70，对 K_VOL 该定 1.5 还是 2.0
   差别很大）。

结论：**改，但不是补 f-string，而是“顶层按类别聚合、明细保留原文、再按代码落盘”。**

### #2 “K线历史不足按根数裂成 7 个 key”—— 真实，且与 #1 同根

### #3 “2026-10-27 产物不完整”—— 产物确实缺，但“中断”解释不成立

事实：`result_2026-10-27.json`（入选 18、名单 18、粗筛池 1197、Σ剔除 1179，完全自洽），
`csv/` 下无对应文件，git 历史里也从未提交过（只有 10-14/10-16/10-23 三个 CSV 进过库）。
全盘 `find` 也没找到副本。

但“当时中断或文件被删”里的**中断可以排除**：写文件的顺序是 CSV 在前、JSON 在后。

```python
# 1634-1648  先写 CSV
with open(csv_path, "w", ...) as fh: ...
# 1651-1690  再组装 result、写 JSON
jdump(res_path, result)
```

单进程顺序执行下只可能有三种结局：
- 崩在 CSV 之前 → 两个都没有；
- 崩在两者之间 → 有 CSV、无 JSON；
- 正常跑完 → 两个都有。

**“有完整 JSON、无 CSV”在这一版代码里不可能由中断产生**，只能是跑完之后被删/被移走
（`git clean`、手工清理、或在另一份 checkout 里跑而 database 是共享的）。所以：
不要按“中断”去加超时/重试，那样修不到点上；该加的是**收尾处的产物成对校验**，
以及让 JSON 自己记录“我这次产出了哪个 CSV、多少行”。

### #5 “mv 数据缺口静默”—— 不是缺口，是设计

`mv_` 的定位（`download_history.py:212`、`screen_kline.py:560`）：只在
**每周采样基准日**（`s_dates`，每 5 个交易日一个）和**本次命中股的 `d*` 日**按需拉取，
是“用到才取”的缓存，不是像 `cross_`/`labels_` 那样的逐日必需序列。

- 10-30 这次两名命中股的 `d*` 都是 10-28，`mv_2026-10-28.json` 存在 → 不缺。
- 10-29 不是采样日，也不是任何命中股的 `d*`，**本来就不该有**。
- 真正必需的输入并没有静默失败：`get_cross`/`get_labels` 失败即 `RuntimeError`；
  `get_mv` 失败也 `RuntimeError`（578-581 行）；`quote` 缺失同样直接终止。
- 按“覆盖区间内 mv 逐日齐全”去登记缺口，会在 10-14/10-16 各报 4 个**假缺口**
  （见审计脚本 C 段），把真问题淹掉。

结论：**不要做“覆盖区间 mv 缺口清单”**。要做就做成“本次实际依赖的数据清单”：

```python
"数据依赖": {
    "粗筛/标签": {"日期": need, "缺失": []},          # 必然为空，缺失即已抛错
    "K线": {"区间": [kbeg, S], "候选": len(pool), "命中": hit_cnt,
             "缺失": km_missing},
    "市值快照": {"使用日期": d_star_days},             # 本次真正读了哪几天
}
```

`K线缺失` 才是唯一可能“静默降级”的一项（非基准日股票取不到会按停牌剔除并只打印告警），
把它写进 JSON 比追 mv 有价值得多。

## 2. 他们没提、但更值得改的

1. **没有按代码的剔除映射**（他们建议 #2 提了，这里强调它是 #1 的替代方案里最好的部分）。
   现在无法回答“某某股为什么没选上”，也无法做误杀排查；`rej` 只有计数。

4. **`剔除原因` 没有区分阶段**：`③ 启动日市值比 < 0.2%` 是 judge 之后的第二道过滤
   （1556-1558 行），与 judge 内的原因混在同一层，做漏斗分析时口径不清。

## 3. 修改建议（按优先级，附可直接落的改法）

### P0-1 剔除原因：顶层聚合 + 明细原文 + 代码映射

一次改动同时解决 #1、#2、以及“无法按代码追溯”。核心是把“归一化”从**唯一账本**
降级为**展示用的聚合键**：

```python
def reason_cat(why):
    """聚合键：抹掉数字，仅用于分层统计；不写入明细。"""
    return re.sub(r"[\d.]+", "#", why)

# [5/6] 循环里
rej_raw, rej_code = {}, {}          # 原文计数 / 代码→原因
...
if det is None:
    rej_raw[why0] = rej_raw.get(why0, 0) + 1
    rej_code[c] = f"find_start: {why0}"
    continue
ok, why = judge(...)
if not ok:
    rej_raw[why] = rej_raw.get(why, 0) + 1
    rej_code[c] = f"judge: {why}"
...
# 第二道过滤同样落 rej_raw / rej_code

rej = {}
for why, n in rej_raw.items():
    k = reason_cat(why)
    rej[k] = rej.get(k, 0) + n
```

写进 result：

```python
"剔除统计": dict(sorted(rej.items(), key=lambda kv: -kv[1])),   # 现在的"剔除非"
"剔除明细": dict(sorted(rej_raw.items(), key=lambda kv: -kv[1])), # 原文，含真实 N/age/日期
"剔除代码": rej_code,                                            # {code: 原因}
"剔除口径": "统计=数字归一化聚合；明细=原文；代码=逐股",
```

兼容性：`剔除非` 建议保留（旧脚本可能在读），新增三个字段即可；若要改名，
在 `版本` 里升到 v3.9 并在 `K线选股规则_v3.md` 的版本沿革登记（该文件 90-102 行有硬性规范）。

`K线历史不足(30根)` 会自动并成 `K线历史不足(#根)`（#2 解决），而明细里仍能看到
6 个具体根数；如果还想更干净，给 `find_start` 的这条加个固定前缀
`K线历史不足`，把根数挪进括号外的明细字段。

```python
if i < MIN_HISTORY:
```

### P1 产物原子写 + 成对校验

```python
def jdump(path, obj):
    os.makedirs(os.path.dirname(path), exist_ok=True)
    tmp = path + ".tmp"
    with open(tmp, "w", encoding="utf-8") as f:
        json.dump(obj, f, ensure_ascii=False)
        f.flush(); os.fsync(f.fileno())
    os.replace(tmp, path)            # 同目录 rename 是原子的
```

CSV 同理（先写 `.tmp` 再 `os.replace`）。收尾处加：

```python
with open(csv_path, encoding="utf-8-sig") as f:
    n_csv = sum(1 for _ in f) - 1
if not (os.path.exists(csv_path) and os.path.exists(res_path)):
    raise RuntimeError("产物缺失：CSV/JSON 未成对生成")
if n_csv != len(final):
    raise RuntimeError(f"产物行数不一致：CSV {n_csv} ≠ 名单 {len(final)}")
```

并把 `"产物": {"csv": os.path.basename(csv_path), "行数": n_csv,
"json": os.path.basename(res_path)}` 写进 result——以后再出现 10-27 那种情况，
JSON 自己就能证明“当时 CSV 确实生成过、多少行”，不用靠推测。

## 4. 关于 #6（财务硬过滤）和 #7（回测小结）

### #6 提议的开关达不到目的

拿本次的田中精机（`sz300461`）验一下：


近四成样本，属于**会改变策略性格**的参数，不该顺手做成默认。建议：

- 开关命名贴合语义：`--require-turnaround`（①②③至少一项“是”）或
  `--exclude-health-danger`（只剔“高危”）；
- 默认关闭，且在 result 里记录“本次是否启用、剔了哪些代码”，否则回测样本不可比；
- 先用 5 批样本回测再决定是否默认开启。
