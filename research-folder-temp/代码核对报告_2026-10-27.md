### 1.3 接口层的隐患

1. **`retry()` 把空结果判定为失败**（两处实现不一致）
   - `screen_kline.retry()` 有 `allow_empty` 参数，`get_labels()` 正确地让第 2 页起返回空也算成功 ✅
   - `download_history.retry()` **没有这个参数**（`download_history.py:92-108`），只有一句 `if r: return r`。`download_labels()` 的分页逻辑（`download_history.py:185-198`）因此存在风险：当某个桶的数量**恰好是 `LABEL_PAGE=500` 的整数倍**时，末页返回空 → 被判失败 → 直接 `raise RuntimeError` 中止整次下载
   - 建议：把 `screen_kline` 的 `allow_empty` 语义移植过去

2. **分批 K 线静默截断** —— 代码里有防御（`--limit 400` + 末日校验 + 逐只重取），✅ 已正确处理，是我见过比较扎实的写法。唯一残留：补取失败后写 `[警告]` 但**仍写入 7 元组短序列**，下次运行因存在缓存不再重试（这在 `screen_kline.py:439-458` 有 `[警告]` 兜底，可接受）

3. **服务端限频** —— `fin_retry()` 的 15s 长退避 + 单批 5 只 + 批间 2.5s 是合理的实测值；但 `TURN_FIN_BACKOFF` 只在异常文本含「限频」时触发，若服务端换了文案就退化成 3s 短退避。**建议改成「任何失败都按指数退避，且上限≥15s」而不是靠匹配中文串**

4. **认证耦合** —— `screen_kline` 用 `importlib` 直接执行 `~/.local/bin/westock` 源文件来复用它的 token 续期逻辑。CLI 一旦改文件名或结构（比如改成目录/包），`_westock_module()` 会失败。现有 `_westock_module()` 的失败处理是把所有 code 标失败而非崩溃 ✅ 可接受，但建议在 README 里写明「本项目依赖 CLI 的内部结构，不是公开 API」

## 2. 设计逻辑核对

### 2.1 正确的部分（值得肯定）

- **新鲜度窗口与扫描周期自洽**：`K = n+1`，`need = hist[-(n+1):]`，`judge()` 要求 `age <= N`。每周跑一次时，各次扫描覆盖的日期块是**首尾相接、无缝无重叠**的 —— 不会漏掉任何启动日 ✅（这点文档没写，但代码是对的）
- **Points-in-time 过滤**：三张财务表 + `judge_top` 的财务全部按 `InfoPublDate <= 基准日` 过滤 ✅ 避免了未来函数，是整套代码里最专业的部分
- **「取数失败 ≠ 数据不存在」的区分**：`gene="无数据"` / 整列留空 / `关联交易不适用` 三态处理 ✅ 没有被静默误读成「否」
- **多道不该产出不可信名单的防线**：横截面字段缺失校验（`:1427`）、行情缺失报错（`:1486`）、启动日净流入缺失报错（`:1500`）、K 线缺失报错（`:1456`）—— 这类「宁可报错也不给错名单」的设计是对的
- **`screen_kline.get_cross()` 的缓存签名** ✅ 参数变更会自动失效，P0-2 确已修复

### 2.2 问题：⑥「启动后未跌破 MA20」是**恒真条件**（P1-5，仍未修）

`screen_kline.py:1299-1313` 的回扫与 `judge()` 的 `screen_kline.py:1363-1366` 检查的是**同一批数据**：

```python
# find_start：从 i 往回数连续站上 MA20 的天数
for j in range(i, 19, -1):
    if m and cl[j] > m: up += 1
    else: break
ci = i - (up - 1)

# judge：检查 ci+1..i 是否都在 MA20 上方
for j in range(det["_ci"] + 1, det["_i"] + 1):
    if not m or cl[j] <= m: return False, "⑥ 启动后跌破 MA20"
```

`cl[j] > ma20[j]` 对 `j ∈ [ci, i]` 是**构造出来的前提**，所以 ⑥ 永远为真，剔除数恒为 0。`result_*.json` 里若出现 `⑥ 启动后跌破 MA20: N`，N 必然是 0。

**影响**：不是错，但 README 3.3 和规则文档都把它列为「核心条件」，读者会以为真有这道风控。真正想要的是「启动后回踩不破启动日低点 / 箱体上沿」。

**建议**：删掉该条件并在文档中标注「⑥ 非独立过滤」，或改写成用 `bars[ci][4]`（启动日最低价）做回踩判据 —— 后者需要重下带 OHLC 的历史 K 线。

### 2.3 问题：`find_start()` 的 20 日上限使 d\* 不是「上穿日」（P1-4，仍未修）

`for j in range(i, 19, -1)` 最多回扫到索引 20。若股票连续 51 天以上在 MA20 上方，`ci` 停在 20，此时 `d*` 只是「回扫边界」，不是真正的上穿点。

当前因为 `age > N`（N≤4）会把这类全部否决，**不产生假阳性**（`审查报告 P1-4` 的结论正确）。但语义不严谨，且未来若放宽 N 就会出错。

**建议**：增加一行断言 `cl[ci-1] <= ma(cl,20,ci-1)`，不满足则说明未找到真上穿点，应返回 `(None, "非真上穿")` 而非一个虚假 `d*`。

### 2.4 问题：ST / 次新只查 d\* 当天，不查 S 日（P1-2，仍未修）

`judge()` 只查 `st_by_day[d0]` / `new_by_day[d0]`。若股票在 d\* 后被 ST 或 S 日已停牌/退市，仍会入选。

**建议**：`judge()` 末尾补一句 S 日复检（`st_by_day[S]` / `new_by_day[S]`），成本几乎为零。

### 2.5 问题：市值比分子用 d\* 日、分母用 S 日（P1-3，仍未修）

`main()` 用 `cross[d*]` 的 `MainNetFlow` ÷ `quote --date S` 的流通市值。当 `age=4` 时分母滞后 4 个交易日，小盘股一周内市值波动可达 10%+，足以让 0.2% 的阈值翻转。

**建议**：`get_quotes()` 增加一次 `--date d*` 的调用（或复用 download_history 已有的 `mv_<d*>.json`）取同一天的市值。

### 2.6 问题：金融行业「不适用」是数据驱动的，存在误判

`turnaround_metrics()` 里 `applicable = gm_applicable or cl_applicable`：只要没有毛利率且没有合同负债，就标「不适用」。这意味着 **一家普通制造业公司若这两个字段恰好缺失，也会被标成「财务行业，四项指标不适用」**，与事实相反。

**建议**：不要按字段缺失猜行业。接口每张表都有 `EnterpriseType` 字段（实测存在，`balance/all` 与 `balancesheet/all` 都返回），应改用它判定，或至少做成「数据缺失」而非「不适用」。

### 2.7 边界：窗口内停牌会让 d\* 落到 `need` 之外，且报错文案误导

`age = i - ci` 是**该股自己的 K 线索引差**，不是市场日历的交易日差。若股票在窗口内停牌若干天，可能出现 `d*` 的实际日期早于 `need[0]`，而 `cross_by_day` 只覆盖 `need` 这几天 → `row0 is None` → 被记为 `③ 启动日(d0)未通过日频条件`。

这是个**误报**：看起来是「该股启动日不合格」，实际是「那天没拉数据」。停牌股最终也会被剔除，所以不影响名单，但会污染 `result_*.json` 的追溯信息。

**建议**：`judge()` 里先判 `if d0 not in cross_by_day: return False, "③ 启动日不在本次覆盖窗口外（该股存在停牌）"`，与真实的日频条件区分开。

## 3. `judge_top.py` 的专项核对

### 3.1 ✅ 与文档一致的部分

四因子计算、相对加速度公式、`|上期增速|` 作分母、`min_abs_base=1.0pp` 判「不可比」、单季口径（不用累计值）、`fmt_pct_frac` 的基数异常保护 —— 与 `README 4.4` / `股价顶部判断_v1.md` 完全吻合，且**正确地回避了自己算出的总分不对外输出**。

### 3.2 ⚠️ 死代码与设计声明冲突

`evaluate()` 的 `judge_top.py:890-918` 明明算出了：

```python
total = 0.0
for _, key, _, _, sc, _, _ in items:
    total += sc * WEIGHTS[key]     # WEIGHTS 合计 1.00
...
verdict = "已进入顶部高风险区" / "顶部风险偏高" / ...
```

并写进 `result`（`judge_top.py:963-965`），但：
- `print_report()` 不打印
- HTML 不渲染
- `--json` 时被显式排除（`judge_top.py:1721-1722`）

而文件的 `__doc__`、README、`--verbose` 输出都说「不合并总分、不自动判断顶部」，日志里还会打 `[完成] 4 个因子独立计算（不合并总分）`。

**判定**：当前对外输出是正确的，无用户可见的错误。但这是一份**与项目核心原则相悖的残留代码**，任何人改动输出层都会立刻打破「不判顶」的承诺。

**建议**：连同 `WEIGHTS` / `SCORE_TABLE` / `PCT_TABLE` / `table_score` / `percentile_score` / `score_factor` / `accel_score` / `completeness` / `drivers` 一起删除；或保留但在所有出口处加注释说明「已废弃、禁止输出」。二者皆可，但**必须二选一**，不能维持现状。

### 3.3 ❌ 股票代码归一化：北交所 920xxx 会被错判为沪市

`judge_top.py:1701-1707`：

```python
if code.startswith(("5","6","9")): code = "sh" + code
elif code.startswith(("0","1","2","3")): code = "sz" + code
elif code.startswith(("4","8")): code = "bj" + code
```

920xxx 是北交所新代码段，会被分到 `sh`。实测服务端标签里确实有 `bj920023 / bj920285 / bj920296` 这类代码。

**建议**：`code.startswith(("920","43","83","87","88"))` → `bj`，且放在 9 分支之前。

### 3.4 ⚠️ K 线分段拉取失败会静默降级

`fetch_kline()` 的 3 段循环里，某段失败只是 `[告警]` 后 `continue`（`judge_top.py:203-205`）。若第 2 段失败，merged 里会**留下一整年的空洞**，而 `cl` 是连续的列表 —— `ret60` 名义上是 60 个交易日，实际跨了 300 多个自然日，250 日高点/分位全失效，且**没有任何提示**。只有全部失败（0 根）才会被 `<30 根` 的检查拦住。

**建议**：段数校验加入联动判断，或至少检查 merged 的日期跨度与 bar 数是否匹配（例如 725 根 / 3 年），不匹配直接报错。

### 3.5 ⚠️ `rolling_max` / `high_stats` 未防护 None

`hi = [fnum(x.get("high")) for x in nodes]` 若任一节点缺 `high`，`rolling_max()` 里的 `vals[dq[-1]] <= v` 和 `high_stats()` 里的 `max(..., key=lambda i: hi[i])` 都会抛 `TypeError`。`cl`（close）有 `if any(v is None...)` 保护，`hi` 没有 —— 不对称。

**建议**：加一句 `if any(v is None for v in hi): return None` 或在 `rolling_max` 内跳过 None。

### 4.1 ❌ `LISTED_YEARS = 3` 完全不参与裁决

全文件只有两处出现：`screen_kline.py:129` 的定义，`screen_kline.py:1644` 写进 `result_*.json` 的参数表。**`judge()` 里的次新剔除用的是 `new_by_day[d0]`，来自 `NEW_LABELS` 四个标签桶，跟这个常量没有任何关系。**

README 3.4 却把它列在「建议先看文档再改」的常量表里 → 使用者改了它，名单不会有任何变化，而且 `result_*.json` 会把修改后的值写进「参数」里，看起来像是生效了。**这是最容易误导复现的一处不一致。**

**建议**：要么删除该常量（并在参数表里改成「次新股口径：NEW_LABELS 四桶并集」），要么真正实现它 —— 用上市日期做 `(S - list_date) >= 3年` 的本地复核，作为服务端标签的交叉验证（后者更有价值，正好弥补 §1.2 提到的「标签语义依赖服务端」风险）。

### 4.2 CHG_HI=20.5% 与可买性

- 文档 §3.2 / P1A 研究把上限从 9.5 放宽到 20.5，**目的就是纳入创业板/科创板涨停日**，同时明确承认「S 日涨停不可买」仍未做 —— 属已知、已登记的设计取舍，不是错误。
- 需注意：`database/cross_*.json` 里 **bj 代码数为 0**（98 个文件全扫描），所以「当前无北交所」的前提仍成立；但 `labels` 体系里北交所股票是存在的。一旦服务端把 bj 纳入 `screen condition` 的结果，**20.5% 上限对 30% 涨跌幅的北交所就不再适用**（它会把 20.5%~30% 的强势启动全砍掉，是一个方向相反的错误）。建议现在就加一条 `bj` 代码的断言/告警。

## 5. 工程实现 bug（按严重度）

### P1 —— `download_history.py --kline-only` 必然崩溃（必修）

`download_history.py:391-393`：

```python
days = sorted(set(os.path.basename(f)[6:-5]
                  for f in glob.glob(os.path.join(DB, "cross_*.json"))))
```

`cross_*.json` 这个 glob **同时匹配到 `cross_<d>.meta.json`**（v2.6 引入的签名文件，`database/` 下现有 5 个），于是 `days` 里混入了 `"2026-10-21.meta"` 这类非法项 —— 实测复现：

```
解析出的日期数 103 | 非法项数 5 | 样例非法: ['2026-10-21.meta','2026-10-19.meta','2026-10-23.meta']
```

随后读 `cross_2026-10-21.meta.json` 得到的是 dict，`for r in dict` 遍历出的是字符串，`r.get("code")` 直接抛 **`AttributeError: 'str' object has no attribute 'get'`**（我在验证过程中原样复现了这个异常）。

**修法**：glob 用 `cross_*.json` 但先 `if f.endswith('.meta.json'): continue`，或改用正则 `re.match(r"cross_(\d{4}-\d{2}-\d{2})\.json$", f)`。

### P2 —— `download_history` 标签分页缺 `allow_empty`

见 §1.3-1。触发条件是「某标签桶数量恰为 500 的整数倍」，概率低但会中止整次下载。

### P2 —— 交易日历存在「2028 年静默失效」的时间炸弹

`get_trading_days()`（`screen_kline.py:308-321`）写死了 `span="2026-06-01"` 和 `--limit 500`。

- 现在（2026-10）距今约 100 个交易日，没问题；
- 到 **约 2028 年年中**，累计交易日超过 500 后，返回会被截断在前 500 条，`days[-1]` 会永远停在 2028 年中的某一天。而 `main()` 里 `S = a.date or days[-1]` —— **既不报错、也不警告，会静默用一个过期的基准日跑出一份看似正常的名单**。

**修法**：span 改成 `min("2026-06-01", end - 3年)`，或在返回条数 `--limit` 时告警；更稳的做法是把起始日也写进缓存 key 和校验。

另外，因为 span 写死，用 `--date 2026-05-xx` 回测会得到「基准日之前交易日不足」而无法运行，属可见的功能限制，建议在 README 里写明。

### P3 —— 陈旧路径引用

`screen_kline.py:18` 的目录结构示意图、规则文档 `:424` `:850` `:860`、`审查报告` 里多处仍指向 `/home/kevin/week_select_stocks/`，实际目录是 `/home/kevin/MyData/kline-select-stocks-approach/`。对一个以「修改登记规范」为荣的项目，这类会误导复现。

### P3 —— 注释与代码不一致

`screen_kline.py:337-341` 的注释说「旧版无 meta 的缓存仅在『默认参数 + 版本 1』时迁移一次」，但紧接的代码已经改成一律重拉（`有一天>-</`）。注释描述的是旧行为。

### P4 —— `--n` 无合法性校验

`--n -1` 会让 `need = hist[0:]`（整个历史），且 `judge()` 里 `det["age"] > N` 恒真/恒假都不报错。建议加 `--n >= 0` 校验。
